# 🗺️ 09.02 — Isolamento de URLs no Django 6.1

O **isolamento de URLs** é a prática de organizar as rotas de cada aplicação em seu próprio arquivo `urls.py`, conectando-as ao projeto por meio de `include()`. Isso deixa o projeto mais legível, modular e fácil de manter — e é a abordagem recomendada pela documentação oficial do Django. 

## 1. A analogia: cidade, mapa e prédios

Pense no seu site Django como uma cidade:

- A **URL** é o endereço digitado pelo usuário.
- O **URLconf** é o mapa que direciona esse endereço.
- A **View** é o prédio que executa o trabalho.
- O `include()` divide o mapa grande em mapas locais de cada bairro (**App**).

Quando alguém acessa `meusite.com/blog/`, o Django consulta primeiro o mapa principal do projeto e depois delega o restante do caminho ao mapa do App `blog`. 

## 2. O mapa principal do projeto (core)

O arquivo `urls.py` do projeto normalmente fica na mesma pasta de `settings.py`. Ele deve conter apenas rotas globais e os pontos de entrada de cada **App**.

```python
# core/urls.py
# 🌍 Mapa-múndi do projeto: define os pontos de entrada globais.

from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    # Painel administrativo do Django.
    # URL final: /admin/
    path("admin/", admin.site.urls),

    # Todas as rotas que começarem com /blog/ serão tratadas
    # pelo arquivo blog/urls.py.
    # URL final: /blog/, /blog/5/, /blog/novo/ etc.
    path("blog/", include("blog.urls")),

    # Exemplo de outro App.
    # URL final: /usuarios/
    path("usuarios/", include("usuarios.urls")),
]
```

### 2.1. Componentes essenciais

| Componente | Função |
|---|---|
| `path()` | Cria uma rota no `urlpatterns`. |
| `include()` | Encaminha parte da URL para o `urls.py` de um App. |
| `admin.site.urls` | Conjunto de rotas pronto do Django Admin. |
| `urlpatterns` | Lista ordenada de rotas verificadas pelo Django. |

O `include()` recebe o módulo de **URLs** do App — por exemplo, `"blog.urls"` — e não apenas uma lista de padrões. 

## 3. O mapa local do App

Cada App deve ter seu próprio `urls.py`. Assim, o App `blog` controla apenas suas próprias rotas.

```python
# blog/urls.py
# 🧩 Mapa local do App 'blog'.

from django.urls import path
from . import views

# Define o namespace da aplicação.
# É obrigatório para usar URLs no formato 'blog:nome_da_rota'.
app_name = "blog"

urlpatterns = [
    # Lista de posts.
    # O prefixo 'blog/' já foi consumido pelo include() no projeto.
    # URL final: /blog/
    path("", views.lista_posts, name="lista"),

    # Detalhe de um post pelo ID.
    # <int:post_id> captura um número e o converte para int.
    # URL final: /blog/5/
    path("<int:post_id>/", views.detalhe_post, name="detalhe"),

    # Criação de um novo post.
    # URL final: /blog/novo/
    path("novo/", views.criar_post, name="novo"),
]
```

> **Dica**:
> ---
> - A rota `""` corresponde exatamente ao caminho restante após o prefixo. 
> - Como o projeto já declarou `blog/`, a URL final é `/blog/`. 
> 

## 4. Namespacing: `app_name`

O `app_name = "blog"` cria um **namespace de aplicação**. Ele **evita conflitos** quando dois Apps possuem rotas com o mesmo nome.

### 4.1. Exemplo do problema

Suponha que `blog` e `loja` tenham ambos:

```python
path("<int:id>/", views.detalhe, name="detalhe")
```

Sem namespace, o Django não saberia qual `detalhe` você deseja usar. Com `namespace`, a referência fica inequívoca:

```python
# URL do App blog
reverse("blog:detalhe")

# URL do App loja
reverse("loja:detalhe")
```

O `namespace` é definido pelo atributo `app_name`, no mesmo nível de `urlpatterns`, dentro do módulo incluído por `include()`.

## 5. URL reversa: nunca escreva URLs fixas

Evite códigos como:

```html
<!-- ❌ Evite: URL fixa e frágil -->
<a href="/blog/5/">Ler post</a>
```

Se o prefixo mudar de `/blog/` para `/artigos/`, todos esses links quebram. Use o nome da rota e o namespace.

| Local | Sintaxe recomendada | Resultado |
|---|---|---|
| Template | `{% url 'blog:detalhe' post.id %}` | Gera `/blog/5/` automaticamente. |
| View | `reverse("blog:lista")` | Retorna `"/blog/"`. |
| Redirect | `redirect("blog:detalhe", post_id=post.id)` | Redireciona para o detalhe do post. |


- `blog/views.py`

```python
# blog/views.py
from django.shortcuts import render, redirect, get_object_or_404
from django.urls import reverse
from .models import Post

def detalhe_post(request, post_id):
    # Busca o post pelo ID ou retorna erro 404 se não existir.
    post = get_object_or_404(Post, pk=post_id)

    return render(request, "blog/detalhe.html", {"post": post})

def criar_post(request):
    # ... lógica de criação do post ...
    # Redireciona usando a URL reversa, sem escrever '/blog/...' manualmente.
    return redirect("blog:detalhe", post_id=5)
```

- `blog/templates/blog/lista.html` 

```html
<!-- blog/templates/blog/lista.html -->
<a href="{% url 'blog:detalhe' post.id %}">
    {{ post.titulo }}
</a>
```

> `Dica:`
> --- 
> - A função `reverse()` e a tag `{% url %}` constróem a URL a partir do nome da rota, respeitando o namespace e os conversores declarados. 

## 6. A ordem das rotas importa

O Django percorre `urlpatterns` **na ordem declarada** e para na primeira rota compatível. 

> Portanto, rotas fixas devem vir antes de rotas genéricas.

### ❌ Errado

```python
# blog/urls.py — EXEMPLO DE ERRO

urlpatterns = [
    # Captura qualquer texto antes de 'novo/'.
    # A URL /blog/novo/ será interpretada como slug='novo'.
    path("<str:slug>/", views.detalhe_post, name="detalhe"),

    # Esta rota nunca será alcançada.
    path("novo/", views.criar_post, name="novo"),
]
```

### ✅ Correto

```python
# blog/urls.py — ORDEM CORRETA

urlpatterns = [
    # Rota fixa e mais específica.
    path("novo/", views.criar_post, name="novo"),

    # Rota genérica com variável.
    path("<str:slug>/", views.detalhe_post, name="detalhe"),
]
```

## 7 Conversores de rota

Os conversores restringem o formato do valor capturado e o convertem para um tipo Python antes de enviá-lo à View. 

| Conversor | Exemplo | Valor recebido na View |
|---|---|---|
| `str` | `<str:slug>` | Texto sem `/` |
| `int` | `<int:post_id>` | Número inteiro (`int`) |
| `slug` | `<slug:slug>` | Letras, números, hífen e underline |
| `uuid` | `<uuid:token>` | Objeto `uuid.UUID` |
| `path` | `<path:caminho>` | Texto que pode conter `/` |



### 7.1. Exemplo de arquivo  `urls.py`


```python
# Exemplos de rotas com conversores.

urlpatterns = [
    # /blog/5/
    path("<int:post_id>/", views.detalhe_post, name="detalhe"),

    # /blog/meu-primeiro-post/
    path("<slug:slug>/", views.detalhe_por_slug, name="detalhe_slug"),

    # /blog/arquivos/2026/relatorio.pdf
    path("arquivos/<path:caminho>/", views.baixar_arquivo, name="arquivo"),
]
```

> `Dica:` 
> ---
> - Para identificadores públicos, prefira `slug`; 
> - Para chaves primárias numéricas, use `int`; 
> - Para caminhos completos, como arquivos, use `path`. 

## 8. Boas práticas finais

- Crie um `urls.py` para cada App.
- Use `include()` no projeto apenas para declarar prefixos globais.
- Defina sempre `app_name` no `urls.py` do App.
- Use `{% url %}`, `reverse()` e `redirect()` com nomes de rota.
- Coloque rotas fixas antes das rotas dinâmicas.
- Prefira conversores como `int` e `slug` para validar e converter valores na URL.
- Não inicie rotas com `/`: escreva `path("blog/", ...)`, e não `path("/blog/", ...)`.
