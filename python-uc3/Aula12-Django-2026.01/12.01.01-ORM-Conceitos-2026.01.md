# Aula 12 — Django ORM: Conceitos

O **Django ORM** (*Object-Relational Mapper*) permite trabalhar com o banco de dados usando classes e objetos Python, sem escrever `SQL` manualmente na maior parte do tempo. Cada **modelo** Django normalmente corresponde a uma **tabela**, cada atributo de **campo** corresponde a uma **coluna** e o ORM gera automaticamente a API de consulta. 

Nesta aula, usaremos como base a aplicação de **receitas**, com os modelos `Categoria` e `Receita`.

## 1. O que é o ORM? 🧠 

O `ORM` traduz operações Python em SQL. Em vez de escrever:

```sql
SELECT * FROM receitas_receita WHERE publicada = true;
```

Você escreve:

```python
Receita.objects.filter(publicada=True)
```

Isso traz vantagens importantes:

- **Produtividade:** consultas comuns ficam mais curtas e legíveis.
- **Segurança:** o `ORM` utiliza `querysets` parametrizados, reduzindo riscos de SQL Injection.
- **Portabilidade:** o mesmo código pode funcionar com **SQLite**, **PostgreSQL**, **MySQL** e **MariaDB**, respeitando as particularidades de cada banco.
- **Manutenção:** os modelos concentram a definição dos dados, validações e relacionamentos.

Um modelo Django é uma classe que herda de `django.db.models.Model`; cada campo é um atributo de classe que representa uma coluna no banco.

## 2. Modelo base da aplicação 📦

Vamos partir deste modelo, já adaptado para uma aplicação de receitas:

```python
from django.contrib.auth.models import User
from django.db import models


class Categoria(models.Model):
    """Representa uma categoria de receita, como Sobremesa ou Jantar."""

    nome = models.CharField(max_length=100)

    class Meta:
        verbose_name = "Categoria"
        verbose_name_plural = "Categorias"
        ordering = ["nome"]

    def __str__(self):
        return self.nome


class Receita(models.Model):
    """Representa uma receita publicada no sistema."""

    titulo = models.CharField(max_length=200)

    ingredientes = models.TextField(
        help_text="Informe um ingrediente por linha."
    )

    modo_preparo = models.TextField(
        help_text="Descreva o passo a passo do preparo."
    )

    tempo_preparo = models.PositiveIntegerField(
        help_text="Tempo total de preparo, em minutos."
    )

    data_publicacao = models.DateTimeField(auto_now_add=True)

    publicada = models.BooleanField(default=False)

    # Relação N:N: uma receita pode ter várias categorias
    # e uma categoria pode estar em várias receitas.
    categorias = models.ManyToManyField(
        Categoria,
        related_name="receitas",
        blank=True,
    )

    # Relação 1:N: cada receita pertence a um autor.
    autor = models.ForeignKey(
        User,
        on_delete=models.CASCADE,
        related_name="receitas",
    )

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
        ordering = ["-data_publicacao"]

    def __str__(self):
        return self.titulo
```

> **Dica**:
> - O Django cria automaticamente uma chave primária `id` quando nenhum campo é marcado com `primary_key=True`. 
> ---

## 3. Propriedades comuns 🏷️

A maioria dos campos aceita **opções comuns**. Elas controlam **validação**, **comportamento** no banco, formulários e **exibição** no Django Admin.

| Opção | Função | Exemplo |
|---|---|---|
| `null` | Permite `NULL` no banco de dados | `null=True` |
| `blank` | Permite valor vazio em formulários | `blank=True` |
| `default` | Define um valor inicial | `default=False` |
| `choices` | Restringe valores a opções pré-definidas | `choices=Dificuldade.choices` |
| `unique` | Garante valores únicos | `unique=True` |
| `db_index` | Cria índice no banco | `db_index=True` |
| `editable` | Define se aparece em formulários | `editable=False` |
| `help_text` | Texto de ajuda | `help_text="Tempo em minutos"` |
| `verbose_name` | Nome legível do campo | `verbose_name="Título"` |
| `validators` | Adiciona validações | `validators=[MinValueValidator(1)]` |
| `error_messages` | Personaliza mensagens de erro | `error_messages={"required": "..."}` |
| `db_column` | Define o nome da coluna no banco | `db_column="titulo_receita"` |
| `db_comment` | Adiciona comentário à coluna | `db_comment="Título da receita"` |
| `db_default` | Valor padrão calculado pelo banco | `db_default=Now()` |
| `primary_key` | Define a chave primária | `primary_key=True` |


> **Dica**: 
> 
> `null` e `blank` são diferentes: 
> - `null=True` afeta o **banco de dados**,  
> - `blank=True` afeta a **validação de formulários**. 
> 
> Para campos de texto, a prática recomendada é usar `blank=True` com `default=""`, evitando dois “estados vazios” diferentes: `NULL` e string vazia. 

### 3.1. Exemplo aplicado às receitas

```python
from django.core.validators import MinValueValidator
from django.db import models


class Receita(models.Model):
    """Representa uma receita publicada no sistema."""

    titulo = models.CharField(
        max_length=200,
        verbose_name="Título",
        help_text="Nome da receita.",
    )

    ingredientes = models.TextField(
        verbose_name="Ingredientes",
        help_text="Informe um ingrediente por linha.",
    )

    modo_preparo = models.TextField(
        verbose_name="Modo de preparo",
        help_text="Descreva o passo a passo do preparo.",
    )

    tempo_preparo = models.PositiveIntegerField(
        verbose_name="Tempo de preparo",
        help_text="Tempo total de preparo, em minutos.",
        validators=[MinValueValidator(1)],
    )

    publicada = models.BooleanField(
        verbose_name="Publicada",
        default=False,
        help_text="Define se a receita está visível no site.",
    )
```

## 4. Campos numéricos 🔢

### 4.1. `IntegerField`

Armazena números inteiros. É adequado para quantidades, anos, contagens e identificadores numéricos simples.

```python
porcoes = models.IntegerField(default=1)
```

### 4.2. `PositiveIntegerField`

Aceita apenas valores não negativos, incluindo o zero. É o campo ideal para `tempo_preparo`, pois minutos não podem ser negativos.

```python
tempo_preparo = models.PositiveIntegerField(
    help_text="Tempo total de preparo, em minutos.",
    validators=[MinValueValidator(1)],
)
```

Aqui, `PositiveIntegerField` impede valores negativos e `MinValueValidator(1)` exige pelo menos 1 minuto.

### 4.3. `DecimalField`

Use `DecimalField` para valores que exigem precisão, especialmente dinheiro. Ele exige `max_digits` e `decimal_places`.

```python
custo_estimado = models.DecimalField(
    max_digits=8,       # Total de dígitos, incluindo as casas decimais
    decimal_places=2,   # Casas decimais
    max_digits=8,
    decimal_places=2,
    help_text="Custo estimado da receita em reais.",
)
```

Por exemplo, `max_digits=8` e `decimal_places=2` permitem valores até `999999.99`.

### 4.4. `FloatField`

`FloatField` armazena números decimais aproximados. Não é a melhor escolha para dinheiro, pois operações de ponto flutuante podem gerar imprecisões.

```python
porcao_em_gramas = models.FloatField(
    help_text="Peso aproximado de uma porção, em gramas.",
)
```

## 5. Campos de texto ✍️

### 5.1. `CharField`

Use `CharField` para textos curtos ou de tamanho limitado, como título, nome e descrição resumida. O parâmetro `max_length` é obrigatório.

```python
titulo = models.CharField(max_length=200)
```

### 5.2. `TextField`

Use `TextField` para textos longos, como ingredientes e modo de preparo. Ele não exige `max_length` no banco, embora seja possível usar `max_length` para validar formulários.

```python
ingredientes = models.TextField(
    help_text="Informe um ingrediente por linha."
)

modo_preparo = models.TextField(
    help_text="Descreva o passo a passo do preparo."
)
```

### 5.3. `SlugField`

`SlugField` é ideal para URLs amigáveis. Um slug converte, por exemplo, “Bolo de Cenoura” em `bolo-de-cenoura`.

```python
from django.utils.text import slugify


class Receita(models.Model):
    titulo = models.CharField(max_length=200)
    slug = models.SlugField(
        max_length=250,
        unique=True,
        blank=True,
    )

    def save(self, *args, **kwargs):
        # Gera o slug automaticamente a partir do título,
        # caso ele ainda não tenha sido definido.
        if not self.slug:
            self.slug = slugify(self.titulo)

        super().save(*args, **kwargs)
```

Com esse campo, uma URL pode ficar assim:

```text
/receitas/bolo-de-cenoura/
```

Em vez de:

```text
/receitas/17/
```

## 6. Campos de data e hora 📅

### 6.1. `DateField`

Armazena apenas uma data, como `2026-11-09`.

```python
data_atualizacao = models.DateField(auto_now=True)
```

### 6.2. `DateTimeField`

Armazena data e hora. É o campo usado em `data_publicacao`.

```python
data_publicacao = models.DateTimeField(auto_now_add=True)
```

### 6.3. `TimeField`

Armazena apenas horário, como `18:30:00`.

```python
horario_ideal = models.TimeField(
    null=True,
    blank=True,
    help_text="Horário recomendado para servir a receita.",
)
```

### 6.4. `DurationField`

Armazena durações, como “2 horas e 30 minutos”.

```python
from datetime import timedelta

tempo_descanso = models.DurationField(
    default=timedelta(minutes=30),
    help_text="Tempo de descanso da massa.",
)
```

### 6.5. `auto_now` e `auto_now_add`

| Opção | Quando é definida | Uso comum |
|---|---|---|
| `auto_now_add=True` | Apenas na criação do objeto | Data de publicação |
| `auto_now=True` | Em cada chamada de `save()` | Data da última atualização |

```python
data_publicacao = models.DateTimeField(auto_now_add=True)
data_atualizacao = models.DateTimeField(auto_now=True)
```

> ⚠️ Atenção:
> --- 
> - Não use `default`, `auto_now` e `auto_now_add` juntos no mesmo campo. Eles são mutuamente exclusivos.
> --- 

## 7. Campos booleanos ✅

`BooleanField` armazena apenas `True` ou `False`.

```python
publicada = models.BooleanField(
    default=False,
    help_text="Define se a receita está visível no site.",
)
```

Para permitir **três estados** — verdadeiro, falso ou indefinido — use `null=True`:

```python
aprovada = models.BooleanField(
    default=None,
    null=True,
    help_text="Indica se a receita foi revisada pela moderação.",
)
```

## 8. Campos de arquivo 🖼️

### 8.1. `FileField`

Use `FileField` para **arquivos genéricos**, como PDFs de fichas técnicas.

```python
arquivo_pdf = models.FileField(
    upload_to="receitas/pdfs/%Y/%m/",
    blank=True,
    null=True,
)
```

### `ImageField`

Use `ImageField` para imagens. Ele **valida** que o arquivo enviado **é uma imagem** e exige a biblioteca **Pillow**.

```python
foto = models.ImageField(
    upload_to="receitas/fotos/%Y/%m/",
    blank=True,
    null=True,
)
```

Para usar **uploads**, configure no `settings.py`:

```python
import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

MEDIA_URL = "/media/"
MEDIA_ROOT = os.path.join(BASE_DIR, "media")
```

E, no `urls.py` do projeto, durante o desenvolvimento:

```python
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import path

urlpatterns = [
    path("admin/", admin.site.urls),
]

if settings.DEBUG:
    urlpatterns += static(
        settings.MEDIA_URL,
        document_root=settings.MEDIA_ROOT,
    )
```

## 9. Relacionamentos 🔗

### 9.1. `ForeignKey` — muitos para um

Uma `ForeignKey` representa uma relação **muitos-para-um**. No nosso caso, várias receitas podem pertencer ao mesmo autor.

```python
autor = models.ForeignKey(
    User,
    on_delete=models.CASCADE,
    related_name="receitas",
)
```

- `User` é o modelo relacionado.
- `on_delete` define o que acontece quando o autor é **excluído**.
- `related_name="receitas"` permite acessar as receitas de um usuário por `usuario.receitas.all()`.

O Django cria automaticamente uma coluna `autor_id` no banco para armazenar a relação. 

#### 9.1.1. Opções de `on_delete`

| Opção | Comportamento |
|---|---|
| `CASCADE` | **Exclui** os objetos relacionados |
| `PROTECT` | **Impede a exclusão** se houver objetos relacionados |
| `RESTRICT` | **Impede a exclusão**, com restrição mais rigorosa |
| `SET_NULL` | Define o campo como `NULL`; exige `null=True` |
| `SET_DEFAULT` | Define o **valor padrão**; exige `default` |
| `SET(valor_ou_funcao)` | Define um **valor específico** |
| `DO_NOTHING` | **Não faz nada**; pode causar erro de integridade |

Para receitas, `CASCADE` é adequado se, ao excluir um usuário, você deseja remover também as receitas dele. Se quiser preservar o conteúdo, considere `SET_NULL` com `null=True`.

```python
autor = models.ForeignKey(
    User,
    on_delete=models.SET_NULL,
    null=True,
    related_name="receitas",
)
```

#### 9.1.2. `related_name`

Sem `related_name`, o Django cria o acesso reverso padrão:

```python
usuario.receita_set.all()
```

Com `related_name="receitas"`, o acesso fica mais claro:

```python
usuario.receitas.all()
```

```python
usuario = User.objects.get(username="luis")
receitas_do_usuario = usuario.receitas.all()
```

### 9.2. `ManyToManyField` — muitos para muitos

Uma receita pode pertencer a várias categorias, e uma categoria pode conter várias receitas. Esse é um relacionamento **muitos-para-muitos**.

```python
categorias = models.ManyToManyField(
    Categoria,
    related_name="receitas",
    blank=True,
)
```

O Django cria automaticamente uma tabela intermediária para armazenar os pares `receita_id` e `categoria_id`. 

```python
receita = Receita.objects.get(titulo="Bolo de cenoura")

# Adiciona categorias
receita.categorias.add(
    Categoria.objects.get(nome="Sobremesa"),
    Categoria.objects.get(nome="Bolos"),
)

# Lista as categorias da receita
receita.categorias.all()

# Lista as receitas de uma categoria
categoria = Categoria.objects.get(nome="Sobremesa")
categoria.receitas.all()
```

#### 9.2.1. Modelo intermediário

Use `through` quando precisar guardar informações sobre a relação, como a ordem das categorias ou uma observação.

```python
class ReceitaCategoria(models.Model):
    """Armazena informações adicionais sobre a relação entre receita e categoria."""

    receita = models.ForeignKey(
        Receita,
        on_delete=models.CASCADE,
        related_name="categoria_receitas",
    )

    categoria = models.ForeignKey(
        Categoria,
        on_delete=models.CASCADE,
        related_name="receita_categorias",
    )

    destaque = models.BooleanField(
        default=False,
        help_text="Indica se a categoria é a principal da receita.",
    )

    class Meta:
        unique_together = ["receita", "categoria"]

    def __str__(self):
        return f"{self.receita} - {self.categoria}"


class Receita(models.Model):
    # ...

    categorias = models.ManyToManyField(
        Categoria,
        through="ReceitaCategoria",
        related_name="receitas",
        blank=True,
    )
```

Com `through`, crie a relação pelo modelo intermediário:

```python
ReceitaCategoria.objects.create(
    receita=receita,
    categoria=categoria,
    destaque=True,
)
```

## 10. `choices` 🎛️

Use `choices` para limitar o campo a opções pré-definidas. A forma moderna e recomendada é usar `TextChoices` ou `IntegerChoices`.

A opção `choices` restringe um campo a um conjunto fixo de valores previamente definidos. Ela é ideal para situações em que o dado tem poucas possibilidades conhecidas, como dificuldade de uma receita, status de publicação ou categoria de refeição. 

O valor armazenado no banco deve ser curto, estável e adequado para consultas; o texto exibido ao usuário deve ser claro e legível. Por exemplo, no banco você pode armazenar `"FACIL"`, mas exibir **“Fácil”** no Django Admin ou em um formulário.

### 10.1 Estrutura das opções 🧩

Cada opção é composta por dois valores:

```python
(VALOR_ARMAZENADO, "Texto exibido ao usuário")
```

| Parte | Função | Exemplo |
|---|---|---|
| Valor armazenado | Valor gravado no banco de dados | `"FACIL"` |
| Rótulo legível | Texto mostrado ao usuário | `"Fácil"` |

No Django, a forma recomendada é criar uma classe herdando de `models.TextChoices` para opções em texto ou `models.IntegerChoices` para opções numéricas.

### 10.2 Exemplo: dificuldade da receita 🍳

Vamos adicionar um campo `dificuldade` ao modelo `Receita`. Ele permitirá classificar cada receita como **fácil**, **média** ou **difícil**.

```python
from django.db import models


class Dificuldade(models.TextChoices):
    """Opções possíveis para a dificuldade de uma receita."""

    FACIL = "FACIL", "Fácil"
    MEDIO = "MEDIO", "Médio"
    DIFICIL = "DIFICIL", "Difícil"
```

### 10.3  Explicação do código

- `class Dificuldade(models.TextChoices)` cria um grupo de opções do tipo texto.
- `FACIL`, `MEDIO` e `DIFICIL` são **constantes** usadas no código Python.
- `"FACIL"`, `"MEDIO"` e `"DIFICIL"` são os valores realmente gravados no banco de dados.
- `"Fácil"`, `"Médio"` e `"Difícil"` são os rótulos que aparecerão para o usuário.
- `Dificuldade.choices` gera automaticamente a lista de tuplas exigida pelo parâmetro `choices`.

O campo pode ser definido assim:

```python
class Receita(models.Model):
    """Representa uma receita publicada no sistema."""

    titulo = models.CharField(max_length=200)

    ingredientes = models.TextField(
        help_text="Informe um ingrediente por linha."
    )

    modo_preparo = models.TextField(
        help_text="Descreva o passo a passo do preparo."
    )

    tempo_preparo = models.PositiveIntegerField(
        help_text="Tempo total de preparo, em minutos."
    )

    dificuldade = models.CharField(
        max_length=10,
        choices=Dificuldade.choices,
        default=Dificuldade.FACIL,
        verbose_name="Dificuldade",
        help_text="Nível de dificuldade para preparar a receita.",
    )

    publicada = models.BooleanField(default=False)

    # ... demais campos e relacionamentos
```

### 10.4 Explicação dos parâmetros

| Parâmetro | Função no exemplo |
|---|---|
| `max_length=10` | Define o tamanho máximo do valor no banco. `"DIFICIL"` possui 7 caracteres, portanto `10` é suficiente. |
| `choices=Dificuldade.choices` | Restringe o campo às três opções definidas na classe `Dificuldade`. |
| `default=Dificuldade.FACIL` | Define `"FACIL"` como valor inicial caso o usuário não informe a dificuldade. |
| `verbose_name="Dificuldade"` | Define o nome legível exibido no Django Admin e em formulários. |
| `help_text="..."` | Exibe uma orientação para quem estiver preenchendo o formulário. |

### 10.5  Como usar no código 🧪 

Para criar uma receita, utilize a constante definida na classe `Dificuldade`:

```python
receita = Receita.objects.create(
    titulo="Bolo de cenoura",
    ingredientes="Cenoura\nFarinha\nOvos\nAçúcar",
    modo_preparo="Misture os ingredientes e asse por 40 minutos.",
    tempo_preparo=45,
    dificuldade=Dificuldade.FACIL,
)
```

Neste caso, o valor salvo no banco será:

```text
FACIL
```

Para consultar receitas de uma determinada dificuldade:

```python
receitas_faceis = Receita.objects.filter(
    dificuldade=Dificuldade.FACIL
)
```

Para atualizar a dificuldade:

```python
receita.dificuldade = Dificuldade.DIFICIL
receita.save()
```

> 🎯 **Dica**:  
>
> Para exibir o rótulo amigável ao usuário, utilize `get_<nome_do_campo>_display()`:
> 
> --- 
> 
> ```python
> receita.get_dificuldade_display()
> # Retorna: 'Fácil'
> ```
> 
> Esse método é gerado automaticamente pelo Django para campos que utilizam `choices`. Ele converte o valor armazenado — por exemplo, `"FACIL"` — no rótulo definido para exibição — `"Fácil"`.
> 
> ---

### 10.6 `IntegerChoices`

Se as opções forem numéricas, utilize `models.IntegerChoices`. Por exemplo, podemos classificar receitas por nível de complexidade:

```python
from django.db import models


class NivelComplexidade(models.IntegerChoices):
    """Níveis numéricos de complexidade de uma receita."""

    BASICO = 1, "Básico"
    INTERMEDIARIO = 2, "Intermediário"
    AVANCADO = 3, "Avançado"
```

No modelo:

```python
class Receita(models.Model):
    # ...

    nivel_complexidade = models.IntegerField(
        choices=NivelComplexidade.choices,
        default=NivelComplexidade.BASICO,
        verbose_name="Nível de complexidade",
        help_text="Classificação da receita conforme a complexidade do preparo.",
    )
```

Aqui:

- `1` será gravado no banco.
- `"Básico"` será exibido ao usuário.
- `NivelComplexidade.BASICO` representa o valor `1` no código Python.

Consulta por nível:

```python
receitas_basicas = Receita.objects.filter(
    nivel_complexidade=NivelComplexidade.BASICO
)
```

Exibição do rótulo:

```python
receita.get_nivel_complexidade_display()
# Retorna: 'Básico'
```

### 10.7 Formas de declarar `choices`

### 10.7.1. `TextChoices` — recomendada para textos

```python
class Dificuldade(models.TextChoices):
    FACIL = "FACIL", "Fácil"
    MEDIO = "MEDIO", "Médio"
    DIFICIL = "DIFICIL", "Difícil"
```

É a melhor escolha quando os valores são strings, como `"FACIL"`, `"MEDIO"` e `"DIFICIL"`.

### 10.7.2. `IntegerChoices` — recomendada para números

```python
class NivelComplexidade(models.IntegerChoices):
    BASICO = 1, "Básico"
    INTERMEDIARIO = 2, "Intermediário"
    AVANCADO = 3, "Avançado"
```

É a melhor escolha quando os valores são inteiros, como `1`, `2` e `3`.

### 10.7.3. Lista de tuplas — forma tradicional

```python
DIFICULDADES = [
    ("FACIL", "Fácil"),
    ("MEDIO", "Médio"),
    ("DIFICIL", "Difícil"),
]


class Receita(models.Model):
    # ...

    dificuldade = models.CharField(
        max_length=10,
        choices=DIFICULDADES,
        default="FACIL",
    )
```

Essa forma funciona, mas `TextChoices` é preferível porque deixa o código mais organizado, permite usar constantes nomeadas e facilita a manutenção.

### 10.8  Cuidados importantes ⚠️

- O valor armazenado deve ser estável: depois que receitas já estiverem cadastradas, alterar `"FACIL"` para `"Fácil"` exigirá uma migração e atualização dos dados existentes.
- O rótulo pode ser alterado livremente, pois ele é apenas o texto exibido ao usuário.
- `choices` valida o valor em formulários e no Django Admin, mas não substitui uma restrição forte no banco de dados.
- Para garantir a restrição também no banco, utilize `CheckConstraint` em `Meta.constraints`.
- Não use `choices` para dados que mudam com frequência ou que serão criados pelos usuários; nesses casos, use um modelo próprio, como `Categoria`.



##  11. Validações 🧪

Validadores garantem que os dados sigam regras de negócio antes de serem salvos.

```python
from django.core.validators import MinValueValidator, MaxValueValidator
from django.db import models


class Receita(models.Model):
    # ...

    tempo_preparo = models.PositiveIntegerField(
        validators=[
            MinValueValidator(1, message="O tempo mínimo é 1 minuto."),
            MaxValueValidator(1440, message="O tempo máximo é 24 horas."),
        ],
    )
```

Também é possível criar validadores personalizados:

```python
from django.core.exceptions import ValidationError


def validar_tempo_preparo(value):
    """Garante que o tempo de preparo seja positivo."""

    if value <= 0:
        raise ValidationError("O tempo de preparo deve ser maior que zero.")
```

## 12. 🗃️ `Meta` e `__str__`

A classe interna `Meta` configura o comportamento do modelo — como ordenação padrão, nomes exibidos no Django Admin e restrições do banco. O método `__str__` define como cada objeto será representado como texto, tornando listas, logs e telas administrativas mais legíveis. 

No modelo `Receita`, usamos:

```python
class Meta:
    verbose_name = "Receita"
    verbose_name_plural = "Receitas"
    ordering = ["-data_publicacao"]

def __str__(self):
    return self.titulo
```

### 12.1. Classe `Meta` 🧩

`Meta` é uma classe interna do modelo. Ela **não cria uma coluna** no banco de dados; em vez disso, informa ao Django regras e configurações sobre como o modelo deve se comportar.

```python
class Receita(models.Model):
    # Campos do modelo...

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
        ordering = ["-data_publicacao"]
```

A indentação é essencial: `class Meta` deve estar dentro da classe `Receita`, no mesmo nível dos campos do modelo.

#### 12.1.1. `verbose_name`

`verbose_name` define o **nome singular legível** do modelo. Ele é usado principalmente no Django Admin, em mensagens do sistema e em formulários gerados automaticamente.

```python
verbose_name = "Receita"
```

Sem essa configuração, o Django usaria o nome da classe e aplicaria regras automáticas de humanização. Como a classe se chama `Receita`, o resultado seria praticamente o mesmo; porém, definir o valor explicitamente torna a intenção clara.

Exemplos de uso:

| Classe do modelo | Sem `verbose_name` | Com `verbose_name` |
|---|---|---|
| `Receita` | `Receita` | `Receita` |
| `Categoria` | `Categoria` | `Categoria` |
| `ItemPedido` | `Item pedido` | `Item do pedido` |

No Django Admin, o nome aparece em títulos, botões e mensagens como:

```text
Adicionar receita
```

```text
A receita “Bolo de cenoura” foi alterada com sucesso.
```

#### 12.1.2. `verbose_name_plural`

`verbose_name_plural` define o **nome plural legível** do modelo. Ele é usado quando o Django precisa se referir a mais de um registro.

```python
verbose_name_plural = "Receitas"
```

No Django Admin, esse nome aparece no menu lateral e no título da listagem:

```text
Receitas
```

O Django tenta criar o plural automaticamente adicionando “s” ao `verbose_name`. Isso funciona para muitas palavras em português, mas pode gerar resultados incorretos em casos como:

```python
verbose_name = "Pão"
```

Sem configuração, poderia gerar `Pãos`; com configuração explícita, você garante o texto correto:

```python
verbose_name = "Pão"
verbose_name_plural = "Pães"
```

No nosso caso, a configuração explícita é uma boa prática:

```python
verbose_name = "Receita"
verbose_name_plural = "Receitas"
```

#### 12.1.3. `ordering`

`ordering` define a **ordenação padrão** aplicada quando você consulta objetos do modelo sem especificar uma ordenação própria.

```python
ordering = ["-data_publicacao"]
```

Aqui:

- `"data_publicacao"` ordena as receitas da mais antiga para a mais recente.
- `"-data_publicacao"` ordena as receitas da mais recente para a mais antiga.
- O hífen `-` indica ordenação **decrescente**.

Como `data_publicacao` é um `DateTimeField` criado com `auto_now_add=True`, ele registra o momento em que a receita foi criada. Portanto, a ordenação abaixo exibe primeiro as receitas mais recentes:

```python
Receita.objects.all()
```

O Django gerará uma consulta equivalente a:

```sql
ORDER BY data_publicacao DESC
```

#### 12.1.4. Ordenação por mais de um campo

É possível definir uma hierarquia de ordenação. Por exemplo, primeiro por data de publicação, do mais recente para o mais antigo; em caso de datas iguais, por título em ordem alfabética:

```python
ordering = ["-data_publicacao", "titulo"]
```

| Configuração | Resultado |
|---|---|
| `["titulo"]` | Ordena por título em ordem alfabética crescente |
| `["-titulo"]` | Ordena por título em ordem alfabética decrescente |
| `["data_publicacao"]` | Ordena da data mais antiga para a mais recente |
| `["-data_publicacao"]` | Ordena da data mais recente para a mais antiga |
| `["-data_publicacao", "titulo"]` | Ordena primeiro por data decrescente e, em caso de empate, por título crescente |

#### 12.1.5. `ordering` não é obrigatório

Você pode sobrescrever a ordenação padrão em uma consulta específica:

```python
Receita.objects.order_by("titulo")
```

Essa consulta ignora `Meta.ordering` e retorna as receitas ordenadas pelo título, em ordem alfabética crescente.

Também é possível remover qualquer ordenação padrão:

```python
Receita.objects.order_by()
```

> ⚠️ **Atenção:** 
> 
>  Em bancos como PostgreSQL, consultas sem ordenação definida não garantem uma ordem previsível dos registros. 
> 
> Por isso, defina `ordering` quando a ordem de exibição for importante.
>

### 12.2. Método `__str__` 🧾

O método `__str__` é um método especial do Python que define a **representação textual de um objeto**. No Django, ele é usado no Django Admin, em mensagens de erro, logs, shells interativos e templates.

```python
def __str__(self):
    return self.titulo
```

Para o modelo `Receita`, cada objeto será representado pelo seu título.

```python
receita = Receita.objects.get(titulo="Bolo de cenoura")

print(receita)
# Bolo de cenoura
```

No Django Admin, em vez de exibir algo técnico como:

```text
Receita object (1)
```

O sistema exibirá:

```text
Bolo de cenoura
```

#### 12.2.1. Por que implementar `__str__`?

Sem `__str__`, o Django exibe uma representação genérica baseada no nome do modelo e na chave primária:

```text
Receita object (1)
```

Isso funciona, mas não ajuda o administrador a identificar rapidamente qual receita está sendo editada. Com `__str__`, a listagem fica muito mais útil:

```text
Bolo de cenoura
Lasanha à bolonhesa
Pudim de leite
```

#### 12.2.2. Exemplo completo

```python
from django.contrib.auth.models import User
from django.db import models


class Categoria(models.Model):
    """Representa uma categoria de receita, como Sobremesa ou Jantar."""

    nome = models.CharField(max_length=100)

    class Meta:
        verbose_name = "Categoria"
        verbose_name_plural = "Categorias"
        ordering = ["nome"]

    def __str__(self):
        return self.nome


class Receita(models.Model):
    """Representa uma receita publicada no sistema."""

    titulo = models.CharField(max_length=200)

    ingredientes = models.TextField(
        help_text="Informe um ingrediente por linha."
    )

    modo_preparo = models.TextField(
        help_text="Descreva o passo a passo do preparo."
    )

    tempo_preparo = models.PositiveIntegerField(
        help_text="Tempo total de preparo, em minutos."
    )

    data_publicacao = models.DateTimeField(auto_now_add=True)

    publicada = models.BooleanField(default=False)

    autor = models.ForeignKey(
        User,
        on_delete=models.CASCADE,
        related_name="receitas",
    )

    categorias = models.ManyToManyField(
        Categoria,
        related_name="receitas",
        blank=True,
    )

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
        ordering = ["-data_publicacao"]

    def __str__(self):
        return self.titulo
```

#### 12.2.3. 🧠 Boas práticas

- Sempre implemente `__str__` em modelos que serão exibidos no Django Admin.
- Retorne um texto curto, único quando possível e facilmente identificável.
- Use `titulo`, `nome`, `codigo` ou uma combinação de campos relevantes.
- Use `Meta.verbose_name` e `Meta.verbose_name_plural` para garantir nomes corretos em português.
- Use `Meta.ordering` quando houver uma ordem padrão natural para os registros.
- Evite consultas muito pesadas dentro de `__str__`; ele pode ser chamado várias vezes em listagens.

Para o modelo `Categoria`, o método é:

```python
def __str__(self):
    return self.nome
```

Assim, uma categoria chamada “Sobremesa” será exibida simplesmente como:

```text
Sobremesa
```

### 13.6. Filtrando receitas

O método `filter()` retorna um `QuerySet` com todos os registros que atendem à condição informada.

#### 13.6.1. Receitas publicadas

```python
Receita.objects.filter(publicada=True)
```

Como a receita foi criada com `publicada=False`, o retorno será vazio:

```text
<QuerySet []>
```

#### 13.6.2. Receitas com tempo menor ou igual a 30 minutos

```python
Receita.objects.filter(tempo_preparo__lte=30)
```

O sufixo `__lte` significa **less than or equal to** — menor ou igual a.

#### 13.6.3. Receitas de uma categoria

```python
Receita.objects.filter(categorias__nome="Sobremesa")
```

Aqui, `categorias__nome` percorre o relacionamento `ManyToManyField` e filtra receitas que possuem uma categoria cujo nome é `"Sobremesa"`.

#### 13.6.4. Categorias com receitas publicadas

```python
Categoria.objects.filter(receitas__publicada=True)
```

Como `related_name="receitas"` foi definido no campo `categorias`, é possível usar `receitas` para consultar a partir de `Categoria`. 

#### 13.6.5. Obtendo um único registro

Use `get()` quando espera **exatamente um** resultado:

```python
receita = Receita.objects.get(titulo="Bolo de cenoura")
```

Se houver mais de uma receita com o mesmo título, o Django lançará `MultipleObjectsReturned`. Se nenhuma receita for encontrada, será lançado `DoesNotExist`.

```python
Receita.objects.get(titulo="Receita inexistente")
```

Erro esperado:

```text
DoesNotExist: Receita matching query does not exist.
```

```python
receita = Receita.objects.get(titulo="Bolo de cenoura")

receita.publicada = True
receita.save()
```

Para confirmar:

```python

```

Saída:

```text

```


#### 13.6.7. Excluindo um registro

```python
receita = Receita.objects.get(titulo="Bolo de cenoura")
```

⚠️ A exclusão é permanente. Antes de executar `delete()`, confirme se selecionou o registro correto.


#### 13.6.11. Boas práticas

- Use `CharField` para textos curtos e `TextField` para textos longos.
- Use `DecimalField` para dinheiro e `FloatField` apenas para medidas aproximadas.
- Prefira `blank=True` e `default=""` em campos de texto opcionais.
- Sempre defina `on_delete` em `ForeignKey` e `OneToOneField`.
- Use `related_name` descritivo para melhorar a legibilidade do código.
- Use `choices` para valores fixos, como dificuldade ou status.
- Use `validators` para regras de negócio, como tempo mínimo de preparo.
- Use `__str__` para representar objetos de forma legível.
- Use `Meta.ordering` apenas quando a ordenação padrão fizer sentido para o modelo.
