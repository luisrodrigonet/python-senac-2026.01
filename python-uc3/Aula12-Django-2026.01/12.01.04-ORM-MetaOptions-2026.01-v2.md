#  Aula 12 — Django ORM: `Meta Options` (Opções de Metadados) 🧩

As **Meta Options** são configurações declaradas dentro da classe interna `Meta` de um modelo. Elas **não criam campos** no banco, mas definem como o Django interpreta, organiza, valida, indexa, documenta e interage com aquele modelo. 

No seu projeto de receitas, elas são úteis para:

- Definir a ordem padrão das receitas e categorias.
- Melhorar os nomes exibidos no Django Admin.
- Garantir regras de integridade no banco.
- Criar índices para consultas mais rápidas.
- Definir permissões específicas, como “pode publicar receita”.

> --- 
> 
> 🎯 **Regra prática:** 
> 
> - use `Meta` para configurações estruturais e de comportamento do modelo. 
> - Use campos (`models.CharField`, `models.DateTimeField`, etc.) para armazenar dados.
>
> --- 

## 1. Estrutura básica 📦

```python
from django.db import models


class Categoria(models.Model):
    """Representa uma categoria de receita, como Sobremesa ou Jantar."""

    nome = models.CharField(max_length=100)

    class Meta:
        # Nome legível singular, usado no Admin e em mensagens.
        verbose_name = "Categoria"

        # Nome legível plural, usado no Admin e em mensagens.
        verbose_name_plural = "Categorias"

        # Ordenação padrão das consultas: ordem alfabética pelo nome.
        ordering = ["nome"]

    def __str__(self):
        return self.nome
```

Aqui, `Meta` não adiciona uma coluna chamada `verbose_name` ou `ordering` ao banco. Ela apenas informa ao Django **como o modelo deve se comportar**. 
## 2. Modelo base da aula 🍽️

Vamos usar este modelo como referência:

```python
from django.contrib.auth.models import User
from django.db import models


class Categoria(models.Model):
    """Representa uma categoria de receita, como Sobremesa ou Jantar."""

    nome = models.CharField(max_length=100)

    class Meta:
        verbose_name = "Categoria"
        verbose_name_plural = "Categorias"
        ordering = ["nome"]

    def __str__(self):
        return self.nome


class Receita(models.Model):
    """Representa uma receita publicada no sistema."""

    titulo = models.CharField(max_length=200)

    ingredientes = models.TextField(
        help_text="Informe um ingrediente por linha."
    )

    modo_preparo = models.TextField(
        help_text="Descreva o passo a passo do preparo."
    )

    tempo_preparo = models.PositiveIntegerField(
        help_text="Tempo total de preparo, em minutos."
    )

    data_publicacao = models.DateTimeField(auto_now_add=True)

    publicada = models.BooleanField(default=False)

    # Relação N:N: uma receita pode ter várias categorias
    # e uma categoria pode estar em várias receitas.
    categorias = models.ManyToManyField(
        Categoria,
        related_name="receitas",
        blank=True,
    )

    # Relação 1:N: cada receita pertence a um autor.
    autor = models.ForeignKey(
        User,
        on_delete=models.CASCADE,
        related_name="receitas",
    )

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
        ordering = ["-data_publicacao"]

    def __str__(self):
        return self.titulo
```

Neste caso:

- `Receita.objects.all()` retornará as receitas **da mais recente para a mais antiga**, por causa do `-` antes de `data_publicacao`.
- No Admin, aparecerão os nomes **“Receita”** e **“Receitas”**, definidos por `verbose_name` e `verbose_name_plural`.
- A partir de uma `Categoria`, você pode acessar as receitas relacionadas com `categoria.receitas.all()`, por causa do `related_name="receitas"`. 

## 3. O que é `Meta`? 🧠

`Meta` é uma **classe interna opcional** do modelo. Ela concentra metadados — informações sobre o modelo, e não sobre um registro específico.

```python
class Receita(models.Model):
    # Campos: dados que serão armazenados no banco.

    class Meta:
        # Metadados: configurações sobre o modelo.
        ordering = ["-data_publicacao"]
```

| Conceito | Exemplo | O que representa |
|---|---|---|
| Campo | `titulo = models.CharField(...)` | Um dado armazenado em cada receita |
| Meta option | `ordering = ["-data_publicacao"]` | Uma regra de comportamento do modelo |
| Instância | `Receita.objects.get(id=1)` | Uma receita específica |
| Modelo | `Receita` | A estrutura e as regras das receitas |

## 4. `verbose_name` e `verbose_name_plural` 🏷️

### 4.1. `verbose_name`

Define o **nome humano e singular** do modelo. É usado principalmente no Django Admin, formulários automáticos, mensagens de erro e documentação interna.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        verbose_name = "Receita"
```

Sem essa opção, o Django usaria o nome da classe, `Receita`, como base. Em português, isso muitas vezes já funciona, mas `verbose_name` deixa a intenção explícita.

### 4.2. `verbose_name_plural`

Define o **nome humano e plural** do modelo.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
```

Isso é especialmente importante em português, pois nem todo plural é formado apenas adicionando `s`.

```python
class Pais(models.Model):
    nome = models.CharField(max_length=100)

    class Meta:
        verbose_name = "País"
        verbose_name_plural = "Países"
```

> ---
> ✅ **Boa prática:** 
> 
> - Sempre defina `verbose_name` e `verbose_name_plural` em projetos em português. 
> - Isso evita nomes estranhos no Admin.
>
> ---

## 5. `ordering` 🔃

`ordering` define a **ordenação padrão** aplicada pelo ORM quando você consulta o modelo.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        ordering = ["-data_publicacao"]
```

Agora, esta consulta:

```python
receitas = Receita.objects.all()
```

Equivale, conceitualmente, a:

```python
receitas = Receita.objects.order_by("-data_publicacao")
```

O `-` significa **ordem decrescente**. Portanto, as receitas mais recentes aparecem primeiro.

### 5.1. Exemplos de ordenação

```python
# Do mais recente para o mais antigo.
ordering = ["-data_publicacao"]

# Ordem alfabética pelo título.
ordering = ["titulo"]

# Primeiro pelas mais recentes; em caso de empate, ordena pelo título.
ordering = ["-data_publicacao", "titulo"]

# Ordena pelo tempo de preparo, do menor para o maior.
ordering = ["tempo_preparo"]
```

###  5.2. uidado com `ordering` ⚠️ 

`ordering` é conveniente, mas não deve ser usado indiscriminadamente em tabelas grandes. Toda consulta padrão que não definir uma ordenação própria receberá a ordenação do `Meta`.

```python
# Usa o ordering do Meta.
receitas = Receita.objects.all()

# Ignora o ordering do Meta e usa esta ordenação específica.
receitas = Receita.objects.order_by("titulo")
```

> ---
> 
> ✅ **Boa prática:** 
> 
> - Defina `ordering` quando houver uma ordem natural e previsível para o modelo, como datas de publicação, nomes ou prioridades.
>
> ---

## 6. `db_table` 🗃️

Por padrão, o Django cria a tabela com um nome no formato:

```text
nome_do_app_nome_do_modelo
```

Por exemplo, se o app se chamar `receitas`, a tabela pode ser:

```text
receitas_receita
```

Com `db_table`, você define outro nome:

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        db_table = "receitas_publicadas"
```

Isso é útil quando:

- Você integra o Django a um banco já existente.
- A empresa possui uma convenção própria de nomes de tabelas.
- Você precisa manter compatibilidade com um sistema legado.

```python
class Cliente(models.Model):
    nome = models.CharField(max_length=100)

    class Meta:
        db_table = "tb_clientes"
```

> ---
>⚠️ **Atenção:** 
> 
> - Mudar `db_table` depois que o projeto já possui migrations exige cuidado. 
> - O Django tratará a mudança como uma alteração de tabela e poderá tentar renomeá-la ou recriá-la, dependendo do contexto.
>
> ---

## 7. `db_tablespace` 🗂️ 

`db_tablespace` define um **tablespace** do banco de dados. Tablespaces são estruturas usadas por alguns bancos, especialmente Oracle, para organizar fisicamente os dados no armazenamento.

```python
class LogAuditoria(models.Model):
    mensagem = models.TextField()

    class Meta:
        db_tablespace = "logs_tablespace"
```

Na maioria dos projetos com PostgreSQL, MySQL, MariaDB ou SQLite, você **não precisará** dessa opção. Se o banco não suportar tablespaces, o Django ignora a configuração. 

## 8. `abstract` 🧬

`abstract = True` transforma o modelo em uma **classe base abstrata**. Ele não gera tabela no banco, mas seus campos e regras são herdados pelos modelos filhos.

```python
from django.db import models


class BaseAuditavel(models.Model):
    """Campos comuns de auditoria para vários modelos."""

    criado_em = models.DateTimeField(auto_now_add=True)
    atualizado_em = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True


class Receita(BaseAuditavel):
    titulo = models.CharField(max_length=200)

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
```

Neste exemplo:

- `BaseAuditavel` **não cria tabela**.
- `Receita` herdará os campos `criado_em` e `atualizado_em`.
- A tabela de `Receita` conterá esses campos normalmente.

### 8.1. Exemplo aplicado ao projeto

```python
class BaseAuditavel(models.Model):
    """Fornece campos de auditoria para modelos do sistema."""

    criado_em = models.DateTimeField(auto_now_add=True)
    atualizado_em = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True


class Receita(BaseAuditavel):
    titulo = models.CharField(max_length=200)
    ingredientes = models.TextField()
    modo_preparo = models.TextField()
    tempo_preparo = models.PositiveIntegerField()
    publicada = models.BooleanField(default=False)

    class Meta:
        verbose_name = "Receita"
        verbose_name_plural = "Receitas"
        ordering = ["-criado_em"]
```
> ---
> 
> ✅ **Quando usar:** 
> 
> - Quando vários modelos compartilham os mesmos campos, como `criado_em`, `atualizado_em`, `ativo` ou `slug`.
>
> ---

## 9. `app_label` 🏷️

`app_label` informa a qual app um modelo pertence. Normalmente, o Django detecta isso automaticamente pela localização do arquivo.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        app_label = "receitas"
```

Você só precisa definir `app_label` quando o modelo está **fora de um app listado em `INSTALLED_APPS`**, por exemplo, em um módulo compartilhado ou em um arquivo especial.

```python
# core/models.py

class ConfiguracaoGlobal(models.Model):
    chave = models.CharField(max_length=100, unique=True)
    valor = models.TextField()

    class Meta:
        app_label = "core"
```

> ---
> 
> ⚠️ **Atenção:** 
> 
> - Não use `app_label` apenas por costume. 
> - Em um app comum, o Django já identifica o app corretamente.
>
> ---

## 10. Managers: `base_manager_name` e `default_manager_name` 🧰

Um **manager** é o objeto pelo qual você faz consultas no ORM. Por padrão, todo modelo possui:

```python
Receita.objects.all()
```

Aqui, `objects` é o manager padrão.

### 10.1. `default_manager_name`

Define qual manager será usado como **manager padrão** do modelo, ou seja, o manager acessado por `Modelo.objects`.

```python
from django.db import models


class ReceitaPublicadaManager(models.Manager):
    """Retorna apenas receitas publicadas."""

    def get_queryset(self):
        return (
            super()
            .get_queryset()
            .filter(publicada=True)
        )


class Receita(models.Model):
    titulo = models.CharField(max_length=200)
    publicada = models.BooleanField(default=False)

    objects = models.Manager()
    publicadas = ReceitaPublicadaManager()

    class Meta:
        default_manager_name = "publicadas"
```

Com isso, `Receita.objects.all()` retornará apenas receitas com `publicada=True`.

> ---
> 
> ⚠️ **Cuidado:** 
> 
> - Isso pode causar confusão. 
> - Em muitos projetos, é melhor manter `objects` retornando todos os registros e criar managers específicos, como `Receita.publicadas.all()`.
>
> ---

### 10.2. `base_manager_name`

Define qual manager será usado pelo Django em operações internas, como acesso por relações e carregamento de objetos relacionados.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        base_manager_name = "objects"
```

Na prática, `base_manager_name` é uma opção avançada. Use-a apenas quando você entende claramente o impacto de managers filtrados em relacionamentos, admin e consultas internas.

## 11. `default_related_name` 🔁

`default_related_name` define o nome padrão usado para acessar um modelo a partir de outro modelo relacionado.

Por padrão, uma `ForeignKey` cria um acesso reverso como:

```python
autor.receita_set.all()
```

Com `default_related_name`, você pode padronizar esse acesso:

```python
class Receita(models.Model):
    titulo = models.CharField(max_length=200)

    autor = models.ForeignKey(
        User,
        on_delete=models.CASCADE,
    )

    class Meta:
        default_related_name = "receitas"
```

Agora:

```python
usuario.receitas.all()
```

retorna todas as receitas daquele usuário.

No seu modelo, porém, você já definiu o nome reverso diretamente no campo:

```python
autor = models.ForeignKey(
    User,
    on_delete=models.CASCADE,
    related_name="receitas",
)
```

Portanto, `usuario.receitas.all()` já funciona. Nesse caso, `default_related_name` não é necessário.

### 11.1. Diferença importante

| Opção | Onde é definida | Função |
|---|---|---|
| `related_name` | No campo de relação | Define o acesso reverso **daquele campo específico** |
| `default_related_name` | Em `Meta` | Define o acesso reverso **padrão para o modelo** |

```python
# related_name: específico para este campo.
autor = models.ForeignKey(
    User,
    on_delete=models.CASCADE,
    related_name="receitas",
)

# default_related_name: padrão para todas as relações reversas.
class Meta:
    default_related_name = "receitas"
```

## 12.  `get_latest_by` 🕒

`get_latest_by` informa ao Django qual campo deve ser usado pelos métodos `latest()` e `earliest()`.

```python
class Receita(models.Model):
    titulo = models.CharField(max_length=200)
    data_publicacao = models.DateTimeField(auto_now_add=True)

    class Meta:
        get_latest_by = "data_publicacao"
```

Agora você pode fazer:

```python
# Receita mais recente.
receita_mais_recente = Receita.objects.latest()

# Receita mais antiga.
receita_mais_antiga = Receita.objects.earliest()
```

Também é possível definir mais de um campo:

```python
class Meta:
    get_latest_by = ["-data_publicacao", "titulo"]
```

> ---
>
> ✅ **Quando usar:** 
> 
> - Quando existe um campo natural para identificar o registro mais recente, como `data_publicacao`, `criado_em`, `atualizado_em` ou um número sequencial.
>
> ---

## 13. `managed` 🚫

`managed = True` é o padrão. Significa que o Django controla o ciclo de vida da tabela: cria, altera e remove a tabela por meio de migrations.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        managed = True  # Padrão.
```

Com `managed = False`, o Django **não cria, altera nem remove** a tabela por migrations.

```python
class RelatorioFinanceiro(models.Model):
    codigo = models.IntegerField(primary_key=True)
    valor = models.DecimalField(max_digits=10, decimal_places=2)

    class Meta:
        managed = False
        db_table = "relatorio_financeiro_legado"
```
> ---
>
>  ✅ **Quando usar:** 
> 
> - Para mapear tabelas criadas e mantidas por outro sistema, uma view de banco ou uma tabela legada.
>
> ---

> ---
>
> ⚠️ **Atenção:** 
> 
> - Com `managed = False`, você continua podendo consultar e salvar objetos, mas as migrations não criarão a tabela automaticamente.
>
> ---

## 14. `order_with_respect_to` 🔢

`order_with_respect_to` permite ordenar objetos em relação a um objeto pai. O Django cria internamente um campo `_order` para armazenar a posição.

```python
class Questionario(models.Model):
    titulo = models.CharField(max_length=200)


class Pergunta(models.Model):
    questionario = models.ForeignKey(
        Questionario,
        on_delete=models.CASCADE,
    )

    texto = models.CharField(max_length=200)

    class Meta:
        order_with_respect_to = "questionario"
```

Isso permite controlar a ordem das perguntas **dentro de cada questionário**.

```python
questionario = Questionario.objects.get(id=1)

# Obtém a ordem atual das perguntas.
questionario.get_pergunta_order()

# Define uma nova ordem para as perguntas.
questionario.set_pergunta_order([2, 1, 3])
```

> ---
> 
> ✅ **Quando usar:** 
> 
> - Em listas ordenáveis, como etapas de um tutorial, itens de um questionário ou faixas de uma playlist.
>
> ---

## 15. `indexes` 🔎

`indexes` cria índices no banco de dados para acelerar consultas frequentes.

```python
from django.db import models


class Receita(models.Model):
    titulo = models.CharField(max_length=200)
    tempo_preparo = models.PositiveIntegerField()
    publicada = models.BooleanField(default=False)

    class Meta:
        indexes = [
            # Índice simples para busca por título.
            models.Index(
                fields=["titulo"],
                name="receita_titulo_idx",
            ),

            # Índice composto para filtrar receitas publicadas por tempo.
            models.Index(
                fields=["publicada", "tempo_preparo"],
                name="receita_publicada_tempo_idx",
            ),
        ]
```

### 15.1. O que é um índice?

Um índice é uma estrutura que ajuda o banco a encontrar registros mais rapidamente, sem precisar percorrer toda a tabela.

```python
# Consulta que pode se beneficiar de um índice em "titulo".
Receita.objects.filter(titulo__icontains="bolo")
```

### 15.2. Índice composto

Um índice composto envolve mais de um campo:

```python
models.Index(
    fields=["publicada", "tempo_preparo"],
    name="receita_publicada_tempo_idx",
)
```

Ele é mais eficiente para consultas que usam os campos na mesma ordem definida no índice:

```python
Receita.objects.filter(
    publicada=True,
    tempo_preparo__lte=60,
)
```

>  ---
> ✅ **Boa prática:** 
> 
> - Crie índices para campos muito usados em filtros, ordenações ou junções. 
> - Não crie índices em excesso, pois eles ocupam espaço e podem tornar inserções e atualizações mais lentas.
>
> ---

## 16. `constraints` 🔐

`constraints` define regras de integridade aplicadas no banco de dados. Elas impedem que dados inválidos sejam gravados, mesmo que alguém contorne a validação do Django.

### 16.1. `CheckConstraint`

Garante que uma condição seja verdadeira.

```python
from django.db import models
from django.db.models import Q


class Receita(models.Model):
    titulo = models.CharField(max_length=200)
    tempo_preparo = models.PositiveIntegerField()

    class Meta:
        constraints = [
            models.CheckConstraint(
                condition=Q(tempo_preparo__gte=1),
                name="receita_tempo_preparo_positivo",
            ),
        ]
```

Aqui, o banco rejeitará uma receita com `tempo_preparo` menor que `1`.

> ---
> 📌 Dica:
> 
> - No Django moderno, use `condition=` em `CheckConstraint`. 
> - O parâmetro `check=` aparece em documentações e exemplos antigos.
>
> --- 

### 16.2. `UniqueConstraint`

Garante que uma combinação de valores seja única.

```python
from django.db import models


class Avaliacao(models.Model):
    receita = models.ForeignKey(
        "Receita",
        on_delete=models.CASCADE,
    )

    usuario = models.ForeignKey(
        User,
        on_delete=models.CASCADE,
    )

    nota = models.PositiveSmallIntegerField()

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["receita", "usuario"],
                name="avaliacao_unica_por_usuario",
            ),
        ]
```

Isso impede que o mesmo usuário avalie a mesma receita mais de uma vez.

### 16.3. `UniqueConstraint` com condição

Você pode criar uma restrição única apenas para determinados registros:

```python
from django.db import models
from django.db.models import Q


class Receita(models.Model):
    titulo = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200)
    publicada = models.BooleanField(default=False)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["slug"],
                condition=Q(publicada=True),
                name="slug_unico_para_receitas_publicadas",
            ),
        ]
```

Neste exemplo, apenas receitas publicadas precisam ter `slug` único.

## 17. `unique_together`: opção legada 🚫

`unique_together` garante que uma combinação de campos seja única.

```python
class Inscricao(models.Model):
    aluno = models.ForeignKey("Aluno", on_delete=models.CASCADE)
    curso = models.ForeignKey("Curso", on_delete=models.CASCADE)

    class Meta:
        unique_together = [("aluno", "curso")]
```

> ---
> ⚠️ **Atenção**: 
> 
> - O Django recomenda usar `UniqueConstraint` dentro de `constraints`. 
> - A opção `unique_together` pode ser descontinuada no futuro e oferece menos recursos. 
>
> ---

✅ **Prefira:**

```python
class Meta:
    constraints = [
        models.UniqueConstraint(
            fields=["aluno", "curso"],
            name="inscricao_unica_por_curso",
        ),
    ]
```

## 18. `index_together`: opção legada ⚠️

`index_together` criava índices compostos:

```python
class Meta:
    index_together = [
        ["cliente", "data"],
    ]
```

Hoje, use `indexes` com `models.Index`:

```python
class Meta:
    indexes = [
        models.Index(
            fields=["cliente", "data"],
            name="pedido_cliente_data_idx",
        ),
    ]
```

✅ **Prefira sempre `indexes`** em projetos novos.

## 19. `permissions` e `default_permissions` 🛡️

### 19.1. `permissions`

Cria permissões personalizadas além das quatro permissões padrão do Django:

- `add`
- `change`
- `delete`
- `view`

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        permissions = [
            (
                "pode_publicar_receita",
                "Pode publicar receitas",
            ),
            (
                "pode_aprovar_receita",
                "Pode aprovar receitas",
            ),
        ]
```

Depois de rodar as migrations, a permissão poderá ser atribuída a usuários ou grupos:

```python
from django.contrib.auth.models import Permission

permissao = Permission.objects.get(
    codename="pode_publicar_receita"
)
```

### 19.2. `default_permissions`

Define quais permissões padrão serão criadas. O padrão é:

```python
default_permissions = ("add", "change", "delete", "view")
```

Para não criar nenhuma permissão padrão:

```python
class LogSistema(models.Model):
    mensagem = models.TextField()

    class Meta:
        default_permissions = ()
```

> ---
> ⚠️ **Atenção:** 
> 
> - `default_permissions` deve ser definido antes de executar `migrate` pela primeira vez para aquele modelo. 
> - Caso contrário, as permissões padrão já terão sido criadas.
>
> ---

## 20. `required_db_features` e `required_db_vendor` 🛡️

### 20.1. `required_db_features`

Define recursos obrigatórios do banco para que o modelo seja considerado durante as migrations.

```python
class Mapa(models.Model):
    localizacao = models.JSONField()

    class Meta:
        required_db_features = ["gis_enabled"]
```

Aqui, o modelo só será migrado em bancos com suporte a GIS habilitado.

### 20.2. `required_db_vendor`

Restringe o modelo a um fornecedor de banco específico.

```python
class ModeloPostgres(models.Model):
    dados = models.JSONField()

    class Meta:
        required_db_vendor = "postgresql"
```

> ---
> ✅ **Quando usar:** 
> 
> - Em projetos que suportam múltiplos bancos e possuem recursos exclusivos de um deles.
>
> ---


> ---
> ⚠️ **Cuidado:** 
> 
> - Essas opções são avançadas e podem dificultar testes e portabilidade entre bancos.
>
> ---

## 21. `select_on_save` ⚙️

`select_on_save` controla o algoritmo usado pelo método `save()`.

Por padrão, o Django tenta atualizar o registro diretamente com `UPDATE`. Com `select_on_save = True`, o Django usa o algoritmo antigo: primeiro faz um `SELECT` para verificar se o registro existe e, depois, decide entre `UPDATE` e `INSERT`.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        select_on_save = True
```

O Django documenta que isso raramente é necessário. Ele pode ser útil em casos muito específicos, como triggers de banco que interferem no comportamento do `UPDATE`. 

> ---
> ✅ **Recomendação:** 
> 
> - Não use `select_on_save` sem uma necessidade concreta.
>
> ---

## 22. `db_table_comment` 📚

`db_table_comment` adiciona um comentário à tabela no banco. Ele é útil para documentar o propósito da tabela para pessoas que acessam o banco diretamente.

```python
class Receita(models.Model):
    # Campos...

    class Meta:
        db_table_comment = (
            "Armazena as receitas culinárias publicadas no sistema."
        )
```

Essa opção é útil principalmente em projetos corporativos, onde o banco é acessado por analistas, DBAs ou outros sistemas.

## 22. Atributos somente leitura 🧾

Alguns atributos existem na API `_meta`, mas **não são definidos** dentro de `class Meta`.

```python
Receita._meta.label
# 'receitas.Receita'

Receita._meta.label_lower
# 'receitas.receita'
```

| Atributo | Exemplo | Uso |
|---|---|---|
| `label` | `receitas.Receita` | Identificação completa do modelo |
| `label_lower` | `receitas.receita` | Identificação em minúsculas |
| `verbose_name_raw` | Interno | Representação interna do `verbose_name` |
| `auto_created` | Interno | Indica se o modelo foi criado automaticamente |

Esses atributos são úteis para ferramentas, testes, serializers e integrações, mas não devem ser configurados manualmente. 

## 23. Exemplo completo 🧱

Aqui está uma versão mais robusta do seu modelo, aplicando boas práticas modernas de Django:

```python
from django.contrib.auth.models import User
from django.db import models
from django.db.models import Q


class Categoria(models.Model):
    """Representa uma categoria de receita, como Sobremesa ou Jantar."""

    nome = models.CharField(max_length=100)

    class Meta:
        # Nome exibido no Admin e em mensagens do Django.
        verbose_name = "Categoria"

        # Nome plural exibido no Admin e em mensagens do Django.
        verbose_name_plural = "Categorias"

        # Ordenação padrão: categorias em ordem alfabética.
        ordering = ["nome"]

        # Índice para acelerar consultas e ordenações pelo nome.
        indexes = [
            models.Index(
                fields=["nome"],
                name="categoria_nome_idx",
            ),
        ]

        # Garante que não existam duas categorias com o mesmo nome.
        constraints = [
            models.UniqueConstraint(
                fields=["nome"],
                name="categoria_nome_unico",
            ),
        ]

    def __str__(self):
        return self.nome


class Receita(models.Model):
    """Representa uma receita publicada no sistema."""

    titulo = models.CharField(max_length=200)

    slug = models.SlugField(
        max_length=200,
        unique=True,
        help_text="Identificador amigável usado na URL da receita.",
    )

    ingredientes = models.TextField(
        help_text="Informe um ingrediente por linha."
    )

    modo_preparo = models.TextField(
        help_text="Descreva o passo a passo do preparo."
    )

    tempo_preparo = models.PositiveIntegerField(
        help_text="Tempo total de preparo, em minutos."
    )

    data_publicacao = models.DateTimeField(auto_now_add=True)

    publicada = models.BooleanField(default=False)

    # Relação N:N: uma receita pode ter várias categorias
    # e uma categoria pode estar em várias receitas.
    categorias = models.ManyToManyField(
        Categoria,
        related_name="receitas",
        blank=True,
    )

    # Relação 1:N: cada receita pertence a um autor.
    autor = models.ForeignKey(
        User,
        on_delete=models.CASCADE,
        related_name="receitas",
    )

    class Meta:
        # Nome legível singular.
        verbose_name = "Receita"

        # Nome legível plural.
        verbose_name_plural = "Receitas"

        # Ordena das receitas mais recentes para as mais antigas.
        ordering = ["-data_publicacao"]

        # Permite usar Receita.objects.latest() e earliest().
        get_latest_by = "data_publicacao"

        # Índices úteis para consultas frequentes.
        indexes = [
            models.Index(
                fields=["publicada", "-data_publicacao"],
                name="receita_publicada_data_idx",
            ),
            models.Index(
                fields=["tempo_preparo"],
                name="receita_tempo_preparo_idx",
            ),
        ]

        # Regras de integridade aplicadas no banco de dados.
        constraints = [
            models.CheckConstraint(
                condition=Q(tempo_preparo__gte=1),
                name="receita_tempo_preparo_positivo",
            ),
        ]

        # Permissões personalizadas para regras de negócio.
        permissions = [
            (
                "pode_publicar_receita",
                "Pode publicar receitas",
            ),
            (
                "pode_aprovar_receita",
                "Pode aprovar receitas",
            ),
        ]

    def save(self, *args, **kwargs):
        """Gera ou atualiza o slug automaticamente a partir do título."""

        # Converte o título em um texto adequado para URL.
        # Exemplo: "Bolo de Chocolate" -> "bolo-de-chocolate".
        self.slug = slugify(self.titulo)

        # Se o chamador informou update_fields, inclui "slug"
        # para garantir que a alteração seja salva no banco.
        update_fields = kwargs.get("update_fields")

        if update_fields is not None and "titulo" in update_fields:
            kwargs["update_fields"] = {"slug"}.union(update_fields)

        # Chama o save() original do Django.
        # Sem esta linha, o objeto não seria persistido no banco.
        super().save(*args, **kwargs)

    def __str__(self):
        return self.titulo
```

## 24. Consultas práticas 🧪

# Todas as receitas, já ordenadas pela data de publicação.
receitas = Receita.objects.all()

# Apenas receitas publicadas.
receitas_publicadas = Receita.objects.filter(publicada=True)

## 25. Tabela-resumo 📊

| Opção | Função | Uso recomendado |
|---|---|---|
| `abstract` | Cria uma classe base sem tabela | Reaproveitar campos em vários modelos |
| `app_label` | Define o app dono do modelo | Modelos fora de apps convencionais |
| `base_manager_name` | Define o manager usado internamente pelo Django | Casos avançados com managers |
| `default_manager_name` | Define o manager acessado por `Modelo.objects` | Projetos com managers personalizados |
| `db_table` | Define o nome da tabela | Integração com banco legado |
| `db_table_comment` | Adiciona comentário à tabela | Documentação do banco |
| `db_tablespace` | Define um tablespace | Bancos que suportam tablespaces |
| `default_related_name` | Define o acesso reverso padrão | Padronizar relacionamentos |
| `get_latest_by` | Define o campo de `latest()` e `earliest()` | Obter registro mais recente ou antigo |
| `managed` | Controla se o Django cria e altera a tabela | Integração com tabelas externas |
| `order_with_respect_to` | Ordena registros em relação a um pai | Listas ordenáveis por categoria ou pai |
| `ordering` | Define a ordenação padrão | Ordenar listagens e consultas |
| `permissions` | Cria permissões extras | Regras de negócio |
| `default_permissions` | Define permissões padrão | Controlar permissões automáticas |
| `proxy` | Cria um modelo sobre a mesma tabela | Criar variações de comportamento |
| `required_db_features` | Exige recursos do banco | Recursos específicos de banco |
| `required_db_vendor` | Exige um banco específico | Recursos exclusivos de um SGBD |
| `select_on_save` | Usa o algoritmo antigo de `save()` | Casos muito específicos |
| `indexes` | Cria índices no banco | Otimizar consultas |
| `constraints` | Cria restrições no banco | Garantir integridade dos dados |
| `unique_together` | Cria unicidade composta | Legado; prefira `UniqueConstraint` |
| `index_together` | Cria índice composto | Legado; prefira `models.Index` |
| `verbose_name` | Nome legível singular | Admin e mensagens |
| `verbose_name_plural` | Nome legível plural | Admin e mensagens |

## 26 Boas práticas ✅

- Use `ordering` com moderação em tabelas grandes.
- Prefira `UniqueConstraint` a `unique_together`.
- Prefira `models.Index` a `index_together`.
- Defina `verbose_name` e `verbose_name_plural` em projetos em português.
- Use `managed = False` somente para tabelas que não pertencem ao Django.
- Use `proxy` para criar variações de comportamento, não para criar novas tabelas.
- Use `constraints` para regras que devem ser garantidas pelo banco.
- Use `indexes` apenas para campos frequentemente filtrados, ordenados ou usados em junções.
- Não use `select_on_save`, `base_manager_name` ou `required_db_vendor` sem necessidade real.

## 27 Exercício prático 🚀

Adicione ao modelo `Receita`:

1. Um índice para `titulo`.
2. Uma restrição que garanta `tempo_preparo` entre `1` e `600`.
3. Uma permissão chamada `pode_destacar_receita`.
4. Uma restrição única que impeça duas receitas com o mesmo `slug`.

Solução sugerida:

```python
from django.db import models
from django.db.models import Q


class Receita(models.Model):
    # Campos...

    class Meta:
        indexes = [
            models.Index(
                fields=["titulo"],
                name="receita_titulo_idx",
            ),
        ]

        constraints = [
            models.CheckConstraint(
                condition=Q(
                    tempo_preparo__gte=1,
                    tempo_preparo__lte=600,
                ),
                name="receita_tempo_preparo_valido",
            ),
            models.UniqueConstraint(
                fields=["slug"],
                name="receita_slug_unico",
            ),
        ]

        permissions = [
            (
                "pode_destacar_receita",
                "Pode destacar receitas na página inicial",
            ),
        ]
```

Depois, execute:

```bash
python manage.py makemigrations
python manage.py migrate
```

As **Meta Options** transformam o modelo em mais do que uma estrutura de dados: elas definem regras de negócio, desempenho, segurança, integração com o Admin e comportamento padrão das consultas.
