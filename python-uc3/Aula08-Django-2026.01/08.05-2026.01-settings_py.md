# Material Didático — Configurações do Django (`settings.py`)

O arquivo `settings.py` concentra toda a configuração de um projeto Django: aplicativos, banco de dados, segurança, middlewares, templates, idioma, fuso horário, arquivos estáticos e mídia. Ele é um módulo Python comum, gerado pelo `startproject`, e suas variáveis definem o comportamento global do projeto. 

Este material usa **Django 6.1** e considera uma estrutura de projeto com a pasta de configuração `config/`.

## 1. Objetivos da aula

Ao final desta aula, você será capaz de:

- Entender a função do arquivo `settings.py`.
- Identificar as configurações essenciais de um projeto Django.
- Configurar templates globais e templates por aplicativo.
- Diferenciar arquivos estáticos de arquivos de mídia.
- Configurar `SQLite` e ` postgresql`.
- Aplicar boas práticas de segurança e organização.
- Servir arquivos de mídia durante o desenvolvimento.

Considere o seguinte projeto chamado `blog`:

```text
blog/
├── config/
│   ├── __init__.py
│   ├── asgi.py
│   ├── settings.py  # <--- Arquivo Settings
│   ├── urls.py
│   └── wsgi.py
├──pages/

│   │   └──pages/
│   ├── __init__.py
│   ├── admin.py
│   ├── apps.py
│   ├── models.py
│   ├── tests.py

│   ├── js/

└── manage.py
```

A pasta `config/` contém as configurações do projeto. O arquivo mais importante dela é `settings.py`. 

## 3. O que é `settings.py`?

`settings.py` é o arquivo onde o Django procura suas configurações. Cada configuração é uma variável Python, normalmente escrita em **letras maiúsculas**. 

Exemplo:

```python
DEBUG = True
ALLOWED_HOSTS = []
LANGUAGE_CODE = "pt-br"
```

O Django lê essas variáveis ao iniciar o projeto e as utiliza para decidir como se conectar ao banco, quais apps carregar, como renderizar templates e como proteger a aplicação. 

> **Regra prática:** 
> - Evite modificar configurações sem entender seu efeito. Algumas delas, como `DEBUG`, `ALLOWED_HOSTS` e `SECRET_KEY`, afetam diretamente a segurança do projeto. 

## 4. `BASE_DIR`

`BASE_DIR` representa o **diretório raiz** do projeto. Ele é criado automaticamente e é essencial para construir caminhos de forma portátil.

```python
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent
```

Explicação:

- `__file__` é o caminho do arquivo `settings.py`.
- `.resolve()` transforma o caminho em caminho absoluto.
- `.parent` acessa a pasta `config/`.
- O segundo `.parent` acessa a raiz do projeto, onde ficam `manage.py`, `templates/`, `static/` e `media/`.

Com `BASE_DIR`, você evita caminhos fixos como:

```python
# Evite
"C:/Users/Luis/projetos/blog/templates"
```

E usa caminhos relativos à raiz:

```python
# Prefira
BASE_DIR / "templates"
```

## 5. `SECRET_KEY`

```python
SECRET_KEY = "django-insecure-valor-gerado-pelo-startproject"
```

A `SECRET_KEY` é usada para assinatura **criptográfica**. Ela participa, por exemplo, de sessões, mensagens, tokens de redefinição de senha e assinatura de dados. 

O Django exige uma `SECRET_KEY` para iniciar. O `startproject` gera automaticamente uma chave aleatória, mas ela é marcada como insegura para produção. 

### 5.1 Boas práticas

- Nunca publique a chave em repositórios públicos.
- Não use a chave gerada pelo `startproject` em produção.
- Em produção, carregue a chave de uma variável de ambiente.
- Ao trocar a chave, mantenha temporariamente a chave antiga em `SECRET_KEY_FALLBACKS` para não invalidar sessões e tokens existentes.

Exemplo usando variável de ambiente:

```python
import os

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
```

## `DEBUG`

```python
DEBUG = True
```

`DEBUG` ativa ou desativa o modo de depuração. Com `DEBUG = True`, o Django exibe páginas de erro detalhadas, o que facilita identificar problemas durante o desenvolvimento. 

**Nunca faça deploy com `DEBUG = True`.** Em produção, erros detalhados podem expor informações do ambiente e da aplicação. 
| Ambiente | Valor recomendado |
|---|---|
| Desenvolvimento | `DEBUG = True` |
| Produção | `DEBUG = False` |

Quando `DEBUG = False`, é obrigatório configurar `ALLOWED_HOSTS` corretamente; caso contrário, as requisições retornarão erro `400 Bad Request`. 

## 6. `ALLOWED_HOSTS`

```python
ALLOWED_HOSTS = []
```

`ALLOWED_HOSTS` define os domínios autorizados a acessar a aplicação. É uma medida de segurança contra ataques baseados no cabeçalho HTTP `Host`.

Em desenvolvimento, com `DEBUG = True` e lista vazia, o Django aceita:

- `localhost`
- `127.0.0.1`
- `[::1]` 

Em produção, informe os domínios reais:

```python
ALLOWED_HOSTS = ["lrodrigodotnet.com", "www.lrodrigodotnet.com"]
```

Se a aplicação estiver atrás de um `proxy` ou `balanceador`, inclua também o domínio usado externamente.

## 7. `INSTALLED_APPS`

`INSTALLED_APPS` define os aplicativos ativos no projeto. Cada app pode fornecer modelos, views, URLs, templates, comandos de gestão, arquivos estáticos e outros recursos. 

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
]
```

### 7.1 Aplicativos padrão

| App | Função |
|---|---|
| `django.contrib.admin` | Interface administrativa do Django.  |
| `django.contrib.auth` | Autenticação, usuários, grupos e permissões.    |
| `django.contrib.contenttypes` | Registro de tipos de conteúdo e suporte a relações genéricas.    |
| `django.contrib.sessions` | Gerenciamento de sessões.    |
| `django.contrib.messages` | Mensagens temporárias para o usuário.
| `django.contrib.staticfiles` | Gerenciamento e coleta de arquivos estáticos. |

### 7.2. Adicionando um app do projeto

Crie um app:

```bash
python manage.py startapp pages
```

Adicione-o em `INSTALLED_APPS` usando sua classe de configuração:

```python
INSTALLED_APPS = [
    "pages.apps.pagesConfig",

    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
]
```

### 7.3. Adicionando um app de terceiros

Instale o pacote e adicione o app:

```sh
pip install django-extensions
```

```python
INSTALLED_APPS = [
    # ...
    "django_extensions",
]
```

### 7.4. Ordem importa

A ordem em `INSTALLED_APPS` pode afetar a **prioridade de templates**, arquivos estáticos e outros recursos com **nomes iguais**. Coloque **apps do projeto antes dos apps de terceiros** quando houver possibilidade de sobreposição de recursos.  

## 8. `MIDDLEWARE`

`MIDDLEWARE` define uma cadeia de **componentes** que **processam requisições e respostas**. A requisição passa pelos middlewares de cima para baixo; a request retorna por eles de baixo para cima.  

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]
```

### Fluxo de execução

```text
Requisição
   ↓
SecurityMiddleware
   ↓
SessionMiddleware
   ↓
CommonMiddleware
   ↓
CsrfViewMiddleware
   ↓
AuthenticationMiddleware
   ↓
MessageMiddleware
   ↓
XFrameOptionsMiddleware
   ↓
View
   ↓
Resposta
   ↑
Middlewares na ordem inversa
   ↑
Cliente
```

### 8.1. Função de cada middleware

| Middleware | Função |
|---|---|
| `SecurityMiddleware` | Aplica melhorias de segurança, como redirecionamento HTTPS quando configurado. |
| `SessionMiddleware` | Habilita suporte a sessões. |
| `CommonMiddleware` | Trata tarefas comuns, como URLs com ou sem barra final. |
| `CsrfViewMiddleware` | Protege contra ataques CSRF. |
| `AuthenticationMiddleware` | Associa a requisição ao usuário autenticado, quando existir. |
| `MessageMiddleware` | Habilita o framework de mensagens. |
| `XFrameOptionsMiddleware` | Ajuda a proteger contra clickjacking. |

O `admin` do Django depende de sessões, autenticação e mensagens. Portanto, se você customizar `MIDDLEWARE`, preserve os middlewares `SessionMiddleware`, `AuthenticationMiddleware` e `MessageMiddleware`.  

## 9. `ROOT_URLCONF`

```python
ROOT_URLCONF = "config.urls"
```

Essa configuração informa ao Django qual módulo contém as rotas principais do projeto. No exemplo, as rotas ficam em `config/urls.py`.

```python
# config/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include(" pages.urls")),
]
```

## 10. `TEMPLATES`

`TEMPLATES` configura os motores de template. O Django permite **mais de um engine**, mas, na prática, a maioria dos projetos usa o backend nativo `DjangoTemplates`. 

```python
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [BASE_DIR / "templates"],   # <-- Pastas Globais
        "APP_DIRS": True, # <-- Habilita os templates das aplicações
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.debug",
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
        },
    },
]
```

### 10.1 `BACKEND`

Define o **motor de template**. O backend padrão do Django é:

```python
"django.template.backends.django.DjangoTemplates"
```

O Django também oferece suporte ao `Jinja2`, mas este curso utiliza o backend nativo.  

### 10.2 `DIRS`

`DIRS` define **pastas globais** de templates, fora dos apps. Por padrão, é uma lista vazia.  

```python
"DIRS": [BASE_DIR / "templates"],
```

Crie a pasta na raiz do projeto:

```text
blog/
├── templates/
│   └── base.html
```

### 10.3 `APP_DIRS`

Com `APP_DIRS = True`, o Django procura templates dentro da pasta `templates/` de cada app instalado.  

```text
 pages/
└── templates/
    └──  pages/
        └── home.html
```

> Dica:
> - A subpasta ` pages/` dentro de `templates/` cria um namespace. Isso evita conflito caso outro app também tenha um arquivo chamado `home.html`.

### 10.4 Context processors

`Context processors` são funções que recebem a requisição e retornam um **dicionário de dados** disponível para **todos** os **templates** renderizados com aquele backend. Eles **evitam repetir dados comuns em todas as views**.  

```python
"context_processors": [
    "django.template.context_processors.debug",
    "django.template.context_processors.request",
    "django.contrib.auth.context_processors.auth",
    "django.contrib.messages.context_processors.messages",
],
```

| Context processor | Disponibiliza |
|---|---|
| `debug` | Informações de depuração no template. |
| `request` | O objeto `request` atual. |
| `auth` | O usuário autenticado e permissões. |
| `messages` | Mensagens temporárias do framework de mensagens. |

## 11. Exemplo prático: `template base`

Crie `templates/base.html`:

```html
<!-- templates/base.html -->
<!DOCTYPE html>
<html lang="pt-br">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>{% block title %}Blog{% endblock %}</title>

    {% load static %}
    <link rel="stylesheet" href="{% static 'css/style.css' %}">
</head>
<body>
    <header class="site-header">
        <h1>Meu Blog</h1>
    </header>

    <main class="container">
        {% block content %}{% endblock %}
    </main>
</body>
</html>
```

Crie `pages/templates/pages/home.html`:

```html
<!--  pages/templates/ pages/home.html -->
{% extends "base.html" %}

{% block title %}Início{% endblock %}

{% block content %}
    <h2>Bem-vindo ao Blog</h2>
    <p>Este conteúdo vem de um template do app <strong> pages</strong>.</p>
{% endblock %}
```

O Django primeiro procura `base.html` em `DIRS`; depois, se necessário, procura nos diretórios de templates dos apps.  

## 12. `DATABASES`

`DATABASES` define as conexões de banco de dados do projeto. O Django exige uma conexão chamada `default`.  

### 12.1 `SQLite`: configuração padrão

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}
```

`SQLite` é ideal para desenvolvimento, estudos e protótipos porque não exige instalação ou servidor de banco separado.  

###  12.2 `postgreSQL`

Para **produção** ou projetos mais robustos, **postgresql** é uma escolha comum.

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends. postgresql",
        "NAME": "blog_db",
        "USER": "blog_user",
        "PASSWORD": "senha_forte",
        "HOST": "localhost",
        "PORT": "5432",
    }
}
```

**Nunca deixe credenciais fixas no código.** Prefira variáveis de ambiente:

```python
import os

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends. postgresql",
        "NAME": os.environ["DB_NAME"],
        "USER": os.environ["DB_USER"],
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ["DB_HOST"],
        "PORT": os.environ.get("DB_PORT", "5432"),
    }
}
```

### 12.3. Comandos relacionados

```bash
python manage.py makemigrations
python manage.py migrate
```

- `makemigrations` **cria** arquivos de **migração** a partir das alterações nos modelos.
- `migrate` **aplica** as **migrações** ao banco de dados.

## 14. `AUTH_PASSWORD_VALIDATORS`

Essa configuração define regras de **validação de senhas**. Ela é importante para aumentar a segurança das contas de usuário.

```python
AUTH_PASSWORD_VALIDATORS = [
    {
        "NAME": "django.contrib.auth.password_validation.UserAttributeSimilarityValidator",
    },
    {
        "NAME": "django.contrib.auth.password_validation.MinimumLengthValidator",
    },
    {
        "NAME": "django.contrib.auth.password_validation.CommonPasswordValidator",
    },
    {
        "NAME": "django.contrib.auth.password_validation.NumericPasswordValidator",
    },
]
```

Esses validadores evitam senhas muito parecidas com dados do usuário, curtas, comuns ou compostas apenas por números.

## 15. `LANGUAGE_CODE` e `TIME_ZONE`

```python
LANGUAGE_CODE = "en-us"
TIME_ZONE = "UTC"
```

Para projetos em português do Brasil:

```python
LANGUAGE_CODE = "pt-br"
TIME_ZONE = "America/Sao_Paulo"
```

- `LANGUAGE_CODE` define o **idioma** padrão da interface e das mensagens do Django.
- `TIME_ZONE` define o **fuso horário** usado pelo projeto.  

## 16. `USE_TZ`

```python
USE_TZ = True
```

Mantenha `USE_TZ = True`. Com essa configuração, o Django armazena **datas e horas em UTC** no banco e **converte para o fuso horário** definido em `TIME_ZONE` quando necessário. Essa prática evita problemas com horário de verão e diferenças entre servidores.

## 17. Arquivos estáticos

Arquivos estáticos são recursos que não mudam por usuário: **CSS**, **JavaScript**, **imagens**, **fontes** e **bibliotecas** front-end. O Django os gerencia por meio do app `django.contrib.staticfiles`. 

### 17.1. `STATIC_URL`

```python
STATIC_URL = "static/"
```

`STATIC_URL` define o prefixo de **URL** usado para acessar arquivos estáticos. 

Em templates, use a tag `static`:

```html
{% load static %}
<link rel="stylesheet" href="{% static 'css/style.css' %}">
<img src="{% static 'img/logo.png' %}" alt="Logotipo">
<script src="{% static 'js/app.js' %}"></script>
```

### 17.2. `STATICFILES_DIRS`

`STATICFILES_DIRS` define **pastas** globais de arquivos estáticos, **fora** dos apps. 

```python
STATICFILES_DIRS = [
    BASE_DIR / "static",
]
```

Estrutura:

```text
static/
├── css/
│   └── style.css
├── js/
│   └── app.js
└── img/
    └── logo.png
```

### 17.3. Arquivos estáticos dentro de apps

Cada app pode ter sua própria pasta `static/`. Use um namespace para evitar conflitos:

```text
pages/
└── static/
    └──pages/
        └── css/
            └──pages.css
```

Uso no template:

```html
{% load static %}
<link rel="stylesheet" href="{% static 'pages/css/pages.css' %}">
```

### 17.4 `STATIC_ROOT`

`STATIC_ROOT` é o **diretório** onde o Django **reúne** todos os **arquivos** estáticos para **produção**. 

```python
STATIC_ROOT = BASE_DIR / "staticfiles"
```

Para coletar os arquivos:

```bash
python manage.py collectstatic
```

O comando copia arquivos dos apps e das pastas definidas em `STATICFILES_DIRS` para `STATIC_ROOT`. 

> **Importante:** 
> - `STATIC_ROOT` não deve estar listado em `STATICFILES_DIRS`. 
> - Ele é o destino da coleta, não uma fonte de busca.
>

## 18. Arquivos de mídia

Arquivos de mídia são **arquivos enviados por usuários**, como fotos de perfil, imagens de  pages e documentos. Eles são diferentes de arquivos estáticos. 

### 18.1 `MEDIA_URL`

```python
MEDIA_URL = "media/"
```

`MEDIA_URL` define o prefixo público para acessar arquivos enviados pelos usuários. 

### 18.2 `MEDIA_ROOT`

```python
MEDIA_ROOT = BASE_DIR / "media"
```

`MEDIA_ROOT` define a **pasta** física onde os `uploads` serão salvos. 

### 18.3 Exemplo de modelo com upload

```python
#  pages/models.py
from django.db import models

class  pages(models.Model):
    titulo = models.CharField(max_length=200)
    capa = models.ImageField(upload_to=" pages/capas/", blank=True, null=True)

    def __str__(self):
        return self.titulo
```

Com essa configuração, uma imagem enviada pode ser salva em:

```text
media/ pagess/capas/nome-da-imagem.jpg
```

Para usar `ImageField`, instale a biblioteca Pillow:

```bash
pip install Pillow
```

## 19. Servindo mídia em desenvolvimento

O `runserver` serve arquivos estáticos automaticamente quando `django.contrib.staticfiles` está habilitado e `DEBUG = True`. 

Arquivos de mídia, porém, precisam de uma rota adicional no `urls.py` principal. 

```python
# config/urls.py
from django.conf import settings
from django.conf.urls.static import static
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include(" pages.urls")),
]

if settings.DEBUG:
    urlpatterns += static(
        settings.MEDIA_URL,
        document_root=settings.MEDIA_ROOT,
    )
```

Esse código funciona apenas em desenvolvimento. Em produção, use **Nginx**, **Apache**, **CDN** ou outro servidor adequado para servir `MEDIA_ROOT` e `STATIC_ROOT`.

## 21. Exemplo prático: mensagens ao usuário

Com o app `django.contrib.messages` habilitado e o **context** processor de mensagens configurado, você pode **exibir avisos** em qualquer template.  )

Em uma view:

```python
from django.contrib import messages
from django.shortcuts import redirect

def criar_pages(request):
    # lógica de criação
    messages.success(request, "pages criado com sucesso!")
    return redirect("pages:home")
```

No `base.html`:

```html
{% if messages %}
    <ul class="messages">
        {% for message in messages %}
            <li class="{{ message.tags }}">{{ message }}</li>
        {% endfor %}
    </ul>
{% endif %}
```

## 23. Erros comuns

| Erro | Causa provável | Solução |
|---|---|---|
| `TemplateDoesNotExist` | Pasta de templates não configurada ou nome incorreto. | Verifique `DIRS`, `APP_DIRS` e a estrutura `app/templates/app/`.    |
| CSS não carrega | `STATIC_URL`, `STATICFILES_DIRS` ou tag `{% static %}` incorretos. | Confirme `STATIC_URL = "static/"` e use `{% load static %}`.   |
| `400 Bad Request` em produção | `ALLOWED_HOSTS` não contém o domínio. | Adicione o domínio correto à lista.    |
| Upload não aparece | `MEDIA_URL` e `MEDIA_ROOT` não configurados ou rota de mídia ausente. | Configure mídia e adicione `static(settings.MEDIA_URL, ...)` apenas em desenvolvimento.  |
| `ImproperlyConfigured` relacionado a `SECRET_KEY` | Chave ausente. | Defina uma `SECRET_KEY` exclusiva e segura.    |

## 24.Resumo

- `settings.py` é o centro de configuração do projeto. 
- `INSTALLED_APPS` define quais apps estão ativos.  
- `DATABASES` define a conexão com o banco; `default` é obrigatória.  
- `MIDDLEWARE` processa requisições e respostas em cadeia.  
- `TEMPLATES` define onde o Django busca templates e quais dados globais estão disponíveis.  
- `STATIC_URL`, `STATICFILES_DIRS` e `STATIC_ROOT` organizam arquivos estáticos. 
- `MEDIA_URL` e `MEDIA_ROOT` organizam arquivos enviados por usuários. 
- `DEBUG = False` e `ALLOWED_HOSTS` configurados são obrigatórios em produção.
